# Base bump assessment: hermes 0.20.4 (v2026.8.18) → 0.21.5 (v2026.9.24)

Prepared 2026-09-28. Read-only: nothing on dc1-1 or in any repo was changed.
Evidence comes from the tag refs (`git show <tag>:<path>`), the live box (read-only `docker exec`/`ls`/`grep`),
the registry API and the GitHub release notes and issues. Wherever I did not run something, the text says so.

**Summary.** The wrapper's base contracts did not change. This is the lowest-risk base change so far. The risk
sits in runtime behaviour. The first boot runs several one-way migrations (config 37→46, state.db schema
26→30 plus a trigram-FTS rebuild). A new loopback API server starts. Compression starts about 3× earlier on
k3. The mobile plugin's device store faces a new thread-concurrency exposure. One latent hazard exists: if a
second profile ever appears, the gateway switches to multiplex mode and can no longer see any secret that
lives only in the container environment. Recommendation: merge #29 first, then go straight to v2026.9.24
through Phase B, with the additions in §6.

Scale: `v2026.8.18..v2026.9.24` = **17,922 commits**, and v2026.8.18 is an ancestor. The deployed commit is
`e624e9fd` (the image label `org.opencontainers.image.revision` on `hermes-dc1:local`), which is exactly the
v2026.8.18 tag. So this time B0 can diff from the tag.

**state.db `SCHEMA_VERSION` 26 → 30** (hermes_state_common.py 8.18:219 → 9.24:239).
- New tables `conversation_generations` and `gateway_heartbeats`, new indexes, and a view `messages_fts_src`.
- **Data migration v29+v30** (hermes_state_schema.py:1055-1058): a **one-time rebuild of the trigram FTS index**
  that removes cron-session and delegate-child rows from `messages_fts_trigram`. It runs under the startup lease
  (600 s) and a cross-process admission gate. If the rebuild fails it returns False and holds `schema_version`
  back (hermes_state_schema.py:395) rather than stamping it. That is fail-safe, but it would repeat on every boot.
- The FTS storage-layout upgrade (v23 external-content) stays **opt-in**
  (`hermes sessions optimize-storage`), so it does not run automatically.
- The live DB is **178 MB** (it was ≈93 MB of backup in August), with a 5.6 MB `-wal` while serving. Its
  filesystem is **`fuse.shfs`** (Unraid). It is not in `_CROSS_VM_FSTYPES = {virtiofs, 9p…}`
  (hermes_state_wal.py:184), so WAL stays on. That is unchanged from today.
- **Downgrade**: I found no "newer schema" refusal in 0.20.4. However, 0.20.4's `_init_fts` drops and recreates
  its own triggers (8.18 hermes_state_schema.py:144/214/380-384). An image-only rollback onto a v30 DB would
  therefore run 0.20.4's trigger definitions over 0.21.5's view. **I cannot tell statically whether that is clean.**
  Treat state.db + config.yaml + kanban.db as restore-from-backup on rollback.
- What 0.21.0–0.21.2 changed, in brief: a rewritten connection registry; the dashboard/gateway/CLI "attach
  read-only first" (#108076, #110934); FTS damage classified as `fts_index` (degrades search, no longer
  fail-closes the turn, #108130); no raw `open()` on a live DB. All of that is in 9.24. **The 0.21.0
  (8.31) and 0.21.1 (9.7) tags are the fragile ones. Do not stop on them.**
- The previous malformed `messages_fts_trigram` was rebuilt on 2026-08-19. The trigram rebuild will now rewrite
  it anyway. **Run `PRAGMA integrity_check` on the cold-backup copy under 3.53.4 before first boot.** If it
  reports malformed, rebuild with 0.20.4 stopped (as in August), so the v30 migration starts from a sound index.
- `kanban.db` also carries 0.21 migrations (kanban hardening). I did not enumerate them. Back it up.
- New this window: control socket `$HERMES_HOME/gateway.sock` (#92447, merged 8/22). Upstream issue
  **#123761** says a bind-mounted HERMES_HOME can fail it permanently with EOPNOTSUPP after a container
  recreate. On `fuse.shfs` it may never bind. It is **non-fatal**: it only disables pause-for-update and
  fleet identify/status, which we do not use. Check the log, but do not block on it.

**Cold backup.** Stop the container, then assert `state.db-wal` is **0 bytes**. The August list is not enough; it
lacks the mobile pairing state and several databases. Use:

## 3. Process model (singleton lock, rendezvous, multiplex, read-only dashboard, `gateway.standalone`)

- **Multiplex default is ON with no opt-out** (gateway_multiplex_mode.py header; `false` is retired and ignored).
  On this box it resolves to **standalone** because only one profile exists
  (`implicit_multiplex_blocker` → `SINGLE_PROFILE_REASON`, :149). There is no `/opt/data/profiles`.
  `persist_resolved_default` never writes on a guard refusal, so config.yaml stays untouched.
- **Latent hazard, new in this window.** If a second profile ever appears (a `hermes profile create` by the
  agent, or Bot Mode or dashboard profile UI), the next boot multiplexes. It then arms the fail-closed secret
  scope, which is built **only from `<profile>/.env`** and never from `os.environ`
  (secret_scope.py:200-230, :372). **Every secret here is container-env only** (KIMI_API_KEY,
  OPENROUTER_API_KEY, SLACK_*), so provider auth and Slack would fail with `UnscopedSecretError`. It is not
  triggered by the bump. It needs a guard in B6, and a line in STATE.md gotchas.
- **Host-wide singleton lock + rendezvous record** (gateway/host_rendezvous.py): one `gateway` role and one
  `serve` role per OS user. They live in `gateway/status.py:_get_lock_dir` →
  `/opt/data/.local/state/hermes/gateway-locks`, the **same dir that already holds the Slack token lock
  today**. flock therefore already works on shfs. Staleness is proved with `(pid, createTime)`, so PID reuse
  across container restarts is handled.
- **Dashboard attach** (main_dashboard.py:810-870): a *second* `hermes dashboard` attaches to a live ROLE_SERVE
  owner and exits 0. Our s6 `dashboard` service is the only one and binds normally. The run script is
  unchanged: `HERMES_DASHBOARD_HOST=0.0.0.0`, port 9119, `s6-setuidgid hermes`. One edge case: an s6 restart
  that lands while the old instance still answers `/api/host/identity` would attach and exit 0, and s6 then
  restarts it again. That is self-healing.
- **Host guard**: bound `0.0.0.0` still accepts any Host (web_server.py:550-575). The only change is stricter
  authority parsing, and `hermes.kite-opah.ts.net` passes. Caddy's plain `reverse_proxy 127.0.0.1:9119` is
  unaffected.
- **Basic auth**: `HERMES_DASHBOARD_BASIC_AUTH_*` is still read straight from `os.environ`
  (plugins/dashboard_auth/_shared.py:46-49), so it is not secret-scoped.
- **"Dashboard opens read-only first"** (#108076) and read-only readers (#110934) are internal. Nothing of ours
  opens state.db.

- **Compat-shim sweep.** `compat_manifest.json` has no entry for any of these (module, name) pairs. This matters
  because `plugin_compat.py:32` **disables** plugins that resolve through a shim from 2026-09-14 onward.
  The other user plugin, `openrouter-image-gen`, lazily imports private `agent.auxiliary_client._select_pool_entry`
  and `_pool_runtime_api_key`, plus `load_config` and `get_hermes_dir`. All four exist at 9.24 by definition.
  Confirm both on the box with `hermes plugins compat <dir>`, which should exit 0.
- **Test suite.** I found no reference to a removed symbol. `test_adapter`'s introspection of
  `BasePlatformAdapter.connect` still holds. I **did not run** the suite; B2 still has to (the 8/19 run was 155/155).
- **#67069** (the `plugins.enabled` gate key): **still OPEN upstream, and the bug is still present at 9.24.**
  `_plugin_api_runtime_gate` (web_server.py:598-633) and `_mount_plugin_api_routes`
  (web_server_dashboard.py:798) still compare only the manifest `name` (`mobile`). **Keep both
  `hermes-mobile` and `mobile` in `plugins.enabled`.**
- **Refresh coalescing #110061 (0.21.3) versus the plugin's rotating RT with one-behind grace.** The single-flight
  is keyed on the sha256 of the presented RT, per provider, with a **30 s success replay cache**
  (refresh_singleflight.py:28, :56-85). Within 30 s, a burst that replays RTₙ gets the cached rotated session
  and never reaches the plugin. That is compatible with the one-behind grace and strictly reduces
  "reuse → revoke" events. **New exposure:** refresh now runs in `run_in_threadpool` (middleware.py:192,
  routes.py:507). At 0.20.4 it ran synchronously on the event loop (8.18 middleware.py:564), which serialized
  it. `DeviceStore` has **no in-process lock**, and `_save` uses one **per-PID** tmp name
  (`.devices.json.<pid>.tmp`, device_store.py:324-340). Two different RTs refreshing concurrently in one
  process can therefore lose an update. Examples: two of the 4 active devices at once, or RTₙ and RTₙ₋₁ from
  one device. The two threads can also interleave on the same tmp inode. The likely symptom is a device bounced
  to re-pair ("refresh token not recognised"). The chance is low, but it rises with more devices.
  **Fix (plugin PR, RED→GREEN first):** a `threading.Lock` around load→modify→save in `rotate_refresh`,
  `revoke*` and the push-token setters, plus a unique tmp name per write (`tempfile.mkstemp` in the dir).
  It is compatible with both core versions, so merge it before the bump (plugin main deploys at boot).
- Minor: at 9.24 coalesced approval followers fire `pre_approval_request` with `coalesced=True`
  (approval_gateway_wait.py:110). The plugin ignores `**_`, so a coalesced follower pushes a duplicate approval
  notification. The fix is optional: `if kwargs.get("coalesced"): return`.
- Credexec, the gws broker and `skills.disabled`: no hermes config keys are involved. The credexec/gws config is
  ours. The key `skills.disabled` still exists (agent/skill_utils.py:308, tools/skills_tool.py:168).
