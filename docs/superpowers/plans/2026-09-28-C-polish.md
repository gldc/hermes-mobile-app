**Goal:** Fix the two client-visible polish bugs Gianluca reported — the broken "Add to chat" attach
sheet, and the composer's `TextInput` staying tall after a long message is sent — with no server or
transport changes.

**Architecture:** Two independent, small fixes. The attach sheet moves from a `flex:1` root wrapping a
header `View` and an unflexed `ScrollView` (fixed numeric detents `[0.6, 0.95]`) to a `fitToContents`
sheet whose root has no competing flex, following the pattern `settings.tsx` already uses successfully.
The composer gets a pure, unit-tested height helper (`nextComposerHeight`) driven by
`onContentSizeChange`, which clears its height override once `value` is empty — instead of relying on
the native `TextInput`'s auto-grow, which does not auto-shrink on iOS when a controlled value is reset
programmatically.

**Tech Stack:** Expo SDK 56 (`expo` ~56.0.11), React Native 0.85.3, `expo-router` ~56.2.10,
`react-native-screens` 4.25.2, TypeScript, Jest (`jest-expo` preset). No new dependencies.

## Review Focus

- **Largest Dynamic Type on the attach sheet.** The spec explicitly flags this as the risk case for
  `fitToContents` (§8.1) and provides a `ScrollView`-root fallback. A plain `fitToContents` `View` could
  clip the last row at `accessibility-extra-extra-extra-large`; Task 2 tests this and applies the
  fallback if it clips.
- **The composer must reset only when `value` becomes empty**, not interfere with a user manually
  deleting text character-by-character (already shrinks correctly today) or with staging a photo with no
  text (composer must start collapsed, not at the last-typed height). Task 4's unit tests and Task 5's
  on-device check both cover this.
- **Light mode must be re-verified independently of dark.** The only screenshot in the spec's "Observed"
  section is dark; the "text shows through" symptom could hide a transparency issue that renders
  differently — or not at all — in light. Task 2 requires an explicit light screenshot, not an assumption
  that fixing dark fixes both.
- **Small phone sizes.** Removing the fixed `[0.6, 0.95]` detents for `fitToContents` changes how much of
  the screen the sheet occupies on a small device. Task 2 screenshots the smallest simulator device
  available, not only the primary dev device.
- **A long (clamped) message must return to exactly one line, not to the 120pt clamp value.** A fix that
  only "un-grows" partially (e.g. resets to `COMPOSER_MAX_HEIGHT` by mistake) would look identical to the
  bug at a glance. Task 4's `test('clearing after a tall message drops the override, not the last
  height')` pins this, and Task 5's on-device check re-confirms it visually.

```ts
// src/lib/composer-height.ts
//
// The composer's multiline TextInput auto-grows via onContentSizeChange, but
// on iOS it does not auto-shrink back to one line when the controlled `value`
// prop is cleared programmatically after a send — it keeps its last-grown
// height until the screen remounts (spec §8.2). nextComposerHeight() is the
// pure decision: an explicit style height, clamped to a max, or `undefined`
// (no override, so the TextInput sizes itself to one empty line naturally)
// once `value` is empty again.

/** Above this, the input scrolls internally instead of growing further. */
export const COMPOSER_MAX_HEIGHT = 120;

export function nextComposerHeight(contentHeight: number, value: string): number | undefined {
  if (value === '') return undefined;
  return Math.min(contentHeight, COMPOSER_MAX_HEIGHT);
}
```
