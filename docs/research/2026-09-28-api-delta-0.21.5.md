# hermes API delta for the mobile app: 0.20.4 → 0.21.5

**Date:** 2026-09-28 · **From:** `v2026.8.18` (0.20.4, live on dc1-1) · **To:** `v2026.9.24` (0.21.5)
**Method:** the same as `docs/research/2026-08-26-api-coverage-audit.md`, with one change: at 0.21.5
the method, event and server-request catalog comes from the committed OpenRPC file
(`apps/shared/src/gateway-contract.openrpc.json`), not from `@method` greps. Many methods now register
through `HandlerRegistry` and are invisible to a decorator grep. 0.20.4 still uses the `@method` and
emit-site greps. I then intersected those lists with `hermes-mobile-app/src` at `main` 9d09258.
Citations: `N:` = `v2026.9.24:`, `O:` = `v2026.8.18:`, `app:` = `hermes-mobile-app/src/`.

## 0. Headline: bumping to 0.21.5 will break approvals in the app

At 0.21.5 the `approval.request` event is gone. The gateway now sends an **approval as a JSON-RPC
request from server to client**. It sends that request only if the client has advertised
`client.capabilities {server_requests: true}` on the current connection. The app sends no such
message. For the app, then:

- `server_requests.send_async` sees that no attached client can answer
  (`N:tui_gateway/server_requests.py:117-122,186-188`, with
  `N:tui_gateway/session_transports.py:38-47`). It calls `on_result(None)` straight away and never
  writes the request frame.
- `on_result(None)` calls `withdraw_gateway_approval(...)` (`N:tui_gateway/server.py:779-788`,
  `N:tools/approval.py:175-189`). **The command does not run**, and the agent is told:
  *"approval was withdrawn before the user answered (the attached client cannot answer approval requests
  (update the Hermes app))"* (`N:tools/approval.py:878-882`).
- The app shows no card, and nothing in the turn waits for one. Every dangerous-command approval
  becomes a silent refusal.

`clarify` changes the same way (§2). The agent gets an empty answer immediately instead of a
3600 s stall. That is better than the stall users report today, but the question is still never shown.

**Gate for the bump:** ship server-request handling in the app first (§3.1), or accept that
approvals and clarify stop working until it ships. The upstream commits are `9f7f2f28c0` (#110521),
`f9d178f78e` and `2afb405337` (#112548).

## 1. Stop / interrupt contract at 0.21.5

### `session.interrupt`
- **Contract** (`N:tui_gateway/contracts/sessions.py:554-570`)
  - params: `{session_id: str, profile?: str|null, expected_hosted_task_id?: str|null}`.
    `extra="forbid"`, so any other key returns error **4000**.
  - result: `{status: "interrupted"|"not_interrupted", interrupted?: bool, turn_isolation?: bool}`.
- **Handler** (`N:tui_gateway/methods_session.py:2124-2152`), runs inline (it is not in
  `_LONG_HANDLERS`, `N:tui_gateway/server.py:161`).
- **Errors**
  - `4001 "session not found"`: the runtime id is stale (`N:tui_gateway/server.py:1150-1166`). Resume
    the stored id.
  - `5019`: compute-host interrupt failed. Only happens with turn isolation on.
  - `5032`: returned through `_sess` → `_wait_agent` (`N:tui_gateway/server.py:885-889`). This can
    **block up to 30 s** if the agent is still building. Normally irrelevant, because a running turn
    already has its agent.
- **The result ignores whether a turn was running.** It returns `{status:"interrupted"}` on an idle
  session too. `not_interrupted` is returned only when `expected_hosted_task_id` doesn't match.
- **What it does** (`N:tui_gateway/session_lifecycle.py:590-641`), in order:
  1. Sets `_turn_cancel_requested` and **clears the server-side prompt queue**: `queued_prompt=None`,
     pops `queued_prompts`, bumps `_queued_prompt_generation` (`:603-607`).
  2. Fires the plugin hook `agent_loop_stopped` (`:608-619`).
  3. Calls `request_hard_interrupt(agent)` (`:621-623`). This aborts the in-flight model HTTP request,
     sets the per-thread tool interrupt flag, signals tool workers, and **propagates a hard interrupt
     to every live child agent** (`N:agent/interrupt_control.py:109-213`).
  4. **New in 0.21.x:** also stops background/async delegations that this session owns, via
     `async_delegation.interrupt_for_session(reason="user_stop")`. Each one returns as an interrupted
     completion (`:627-631`).
  5. `_clear_pending(sid)` (`N:tui_gateway/server.py:1399-1403`) → `server_requests.cancel(sid,
     "interrupted")` (`N:tui_gateway/server_requests.py:259-273`). This withdraws every open
     server→client request for the session: clarify, sudo, secret, and approval.
  6. `resolve_gateway_approval(key, "deny", resolve_all=True)` (`:638-640`).
  7. Retires the crash-recovery turn marker, so a later `session.resume` will not auto-continue the
     turn the user stopped (`methods_session.py:2146-2151`).
- **Events the client sees after an interrupt**
  - One `request.cancel {id, method, reason:"interrupted"}` per open request
    (`N:tui_gateway/contracts/server_requests.py:215-230`). A queue-backed approval that another path
    already settled produces `reason:"resolved"` or `"session_closed"` instead
    (`N:tools/approval_gateway_wait.py:182-192`).
  - When the run thread unwinds, `message.complete` arrives with `status:"interrupted"` and
    `text` = partial reply. The "Operation interrupted: waiting for model response" sentinel is
    blanked (`N:tui_gateway/prompt_turn.py:304-331,824`, `TurnStatus` at
    `N:tui_gateway/contracts/events.py:137-142`). It also carries `usage` and, when available,
    `persisted_turn`.
  - Interrupted children emit `subagent.complete` with `status:"interrupted"` (enum at
    `N:tui_gateway/contracts/common.py:176-186`).
  - No `error` event and no dedicated `interrupt.ack` event.
- **Tool execution: honored at a boundary, not by pre-emption.** The model request is aborted
  immediately. Tools are signalled through the thread-scoped interrupt flag. Tools that poll it stop
  promptly; the foreground `terminal` subprocess is killed (per the comment at
  `O:tui_gateway/methods_session.py:3185-3188`). Any other tool finishes its current call, and the loop
  exits at the next check. Background processes the agent started are not reaped. **Not verified:**
  which specific tools ignore the flag.
- **Pending prompts**
  - Approvals: never run.
  - Clarify: the blocked wait returns `None`, so the tool gets `""`. A batch gets
    `{"responses":[…all ""…]}` without `timed_out` (`N:tui_gateway/server.py:1339-1356`,
    `N:tools/clarify_tool.py:139-178`).
- **Differences vs 0.20.4** (`O:tui_gateway/methods_session.py:3129-3200`)
  - 0.20.4 did steps 1, 3, 5 and 6, but step 5 released prompts by setting `_answers[rid] = ""`,
    which emits nothing (`O:tui_gateway/server.py:3532-3545`).
  - 0.20.4 did **not** stop async delegations, did **not** retire the turn marker, did not fire the
    plugin hook, and had no `expected_hosted_task_id`.

### Queued prompts and `/goal`
- **Is there a queue RPC?** No. The only way to queue is `prompt.submit` on a busy session.
  `N:tui_gateway/methods_prompt.py:636-654` → `_handle_busy_submit`
  (`N:tui_gateway/session_auto_continue.py:248-291`). Behaviour depends on `display.busy_input_mode`
  (`interrupt` by default):
  - Text-only input in `interrupt` mode: **redirects** the live turn → result `{status:"redirected"}`.
  - Text-only input in `steer` mode: **steers** → result `{status:"steered"}`.
  - Otherwise (including `queue` mode): enqueues the prompt → result `{status:"queued"}`. In
    `interrupt` mode it also hard-interrupts the live turn.
  - `params.queued=true` forces queue mode ("run after", never a correction).
  - The only `4009` from `prompt.submit` is a busy session plus a truncation request, and "subagent
    still running" on a lazy watch session (`N:methods_prompt.py:540,650`).
- **Unchanged from 0.20.4:** the same busy modes and the same statuses
  (`O:tui_gateway/server.py:537-542,8045-8140`).
- **What "live dock" means.** The v0.21.5 release notes mention a "live dock showing the standing
  `/goal` and queued prompts in the CLI and TUI". I found no new queue RPC or queue event behind it,
  so it appears to be client-side rendering.
  - Queue visibility on the wire: only `session.resume`'s `queued: {user}` snapshot
    (`N:tui_gateway/contracts/sessions.py:46-47,91`).
  - `/goal` state is exposed through the new `session.control.read` and `session.control` RPCs and the
    `session.control.update` event (§5).

### `session.steer`, `session.redirect`, `subagent.steer`, `subagent.interrupt`
- **`session.steer` / `session.redirect`**
  - params: `{session_id, text, profile?}`. result: `{status: "queued"|"redirected"|"rejected", text}`
    (`N:contracts/sessions.py:573-591`, handler `N:methods_session.py:2174-2207`).
  - Errors: `4002` empty text, `4001` stale session, `4010` agent doesn't support it, `5000` failed.
  - **Changes vs 0.20.4** (`O:methods_session.py:3406-3440`):
    - Steering an **idle** session now returns `rejected`, and the client should send the text as a
      normal prompt (`:2195-2196`).
    - The steer text now arrives as **its own user row after the current tool batch**
      (`N:agent/interrupt_control.py:244-253`). At 0.20.4 it was appended to the last tool result
      (`O:run_agent.py:3379-3389`).
- **`subagent.steer`**
  - params: `{session_id, subagent_id, text, profile?}`. result:
    `{status:"queued"|"rejected", subagent_id, text}` (`N:contracts/billing_delegation_pets.py:400-419`,
    handler `N:methods_session.py:2225-2240`).
  - Authority: the caller's socket must be **attached to that session**
    (`N:tui_gateway/server.py:864-881`), and authority follows the session's live transport slot after
    resume (`N:tools/delegate_tool_registry.py:107-121`).
  - Behaviour unchanged from 0.20.4.
- **`subagent.interrupt`**
  - params: `{session_id, subagent_id, profile?}`. result: `{found, subagent_id}`
    (`N:contracts/profiles_vault_complete_foreign_subagents.py:628-638`, handler
    `N:tui_gateway/methods_subagents.py:66-87`).
  - **Breaking vs 0.20.4:** 0.20.4 needed only `subagent_id` (`O:methods_session.py:3231-3239`).
    0.21.5 needs `session_id` and ownership, and returns `4001 "session not found or not owned by this
    transport"` otherwise.

## 2. Clarify contract at both tags, with approval for comparison

**Why the app shows nothing today:** at 0.20.4, clarify arrives as the `clarify.request` event.
`app:app/chat/[id].tsx:349-400` has no case for it. The agent thread therefore blocks for the full
clarify timeout (**3600 s by default**) and then gets `""`.

| | 0.20.4 (`v2026.8.18`) | 0.21.5 (`v2026.9.24`) |
|---|---|---|
| Delivery | **Event** `clarify.request` through `_block()` (`O:tui_gateway/server.py:3472-3516`), wired at `O:server.py:6179-6193` | **Server→client request** `{"jsonrpc":"2.0","id":"srq-<12hex>","method":"clarify","params":{…}}` (`N:tui_gateway/server_requests.py:48,61-63`, `N:server.py:1339-1356`). No event. |
| Payload | `{question, choices: [str]\|null, multi_select?: true, request_id: "<8hex>"}`. `multi_select` is present only when true. `choices` null means open-ended (`O:server.py:3477,6187-6191`). | **Single:** `{session_id, question, choices, multi_select?:true}`. **Batch:** `{session_id, questions:[{qid, question, choices:[str]\|null, multi_select:bool}]}`, 1–5 entries. A reconnect replay adds `answers:{qid:str}` for answers already locked (`N:tui_gateway/contracts/server_requests.py:32-59`). The id is the frame's JSON-RPC `id`; there is no `request_id` param. |
| Multi-question? | **No.** The tool signature is `(question, choices, multi_select)` (`O:tools/clarify_tool.py:153-158`). | **Yes, and it is the default.** The schema tells the model to always use `questions` (`N:tools/clarify_tool.py:9-10,244-260`). Mobile must implement the batch shape. |
| Choices / free text | Up to 4 choices; the first is suffixed "(Recommended)". A multi-select answer is a JSON array or a comma-separated string (`N:clarify_tool.py:78-99`, `_clean_answer` at `:89`). |
| How to answer | RPC `clarify.respond {request_id, answer}` → `{status:"ok"}`, or `{status:"expired"}` after timeout (`O:tui_gateway/methods_prompt.py:1400-1406`, `O:server.py:11712-11723`) | **Response frame** with the same id: single → `{"result":{"answer":"…"}}`, where `""` means skip. | Timeout | `agent.clarify_timeout` (a legacy `clarify.timeout` overrides it); default **3600 s**; `<=0` means unlimited. 300 s is used only if config fails to load (`O:tools/clarify_gateway.py:531-574`, `O:server.py:3519-3529`) | Same key and default (`N:tools/clarify_gateway.py:259-285`, `N:server.py:1329-1336`) |
| What the agent sees on timeout | `user_response: ""`, plus a `clarify.expire {request_id}` event (`O:server.py:3502-3515`) | Single: `user_response: ""`. Batch: `{"responses":[…locked or ""…], "timed_out": true}` (`N:server_requests.py:173-179`, `N:clarify_tool.py:139-156`). Plus `request.cancel {id, method:"clarify", reason:"timeout"}`. |
| On interrupt | Released with `""`; nothing is emitted (`O:server.py:3532-3545`) | `request.cancel …reason:"interrupted"`; the tool gets `""` or an all-blank batch |
| On disconnect | The wait keeps running. `session.resume` returns `pending_clarify` (`O:server.py:1939-1956,8784-8785`) | The wait keeps running: no attached client counts as "answerable" (`N:session_transports.py:38-47`). `session.resume`, `session.activate` and `session.events.since` return it in **`open_requests`** (`N:server.py:727-740`, `N:contracts/sessions.py:93`). The client handles each entry as if it had just arrived. |
| Old client (never sends `client.capabilities`) | n/a | **Fails fast.** `send()` returns `None` without writing the frame (`N:server_requests.py:152-153`). The single tool gets `""`, the batch gets all blanks and no `timed_out`, so the agent reads it as "user skipped" (`N:clarify_tool.py:169-178`). |

**Approval, for comparison.**
- **0.20.4**
  - Event `approval.request`, whose payload is `_approval_request_payload(data)`: the tool's dict plus
    `choices` and a redacted `command` (`O:server.py:1922-1936,1971-1979`).
  - Answered with RPC `approval.respond {session_id, choice, all?}` → `{resolved:int}`
    (`O:methods_prompt.py:1486-1500`). This is what `app:app/chat/[id].tsx:291-330` implements.
- **0.21.5**
  - Server request `method:"approval"`. params: `{session_id, request_id, command, description,
    choices:["once"|"session"|"always"|"deny"], allow_permanent?, allow_session?, smart_denied?,
    tool_name?, gateway_session_id?, …extra}` (`N:contracts/server_requests.py:66-95`, builder
    `N:server.py:711-724`).
  - The response frame's result is `{choice, all?}`, which maps to
    `resolve_gateway_approval(choice, resolve_all=all, request_id)` (`N:server.py:779-792`).
  - **`approval.respond` is still accepted.** params `{session_id, choice?, all?, request_id?}`
    (`N:contracts/prompt_voice.py:316-330`). But the app never learns that a request exists without
    the server-request path, and the gateway **withdraws** the approval for a non-advertising client
    (§0).
  - Still available: `approval.pending` and `approval.received`, the latter starting the timeout clock
    (`N:contracts/prompt_voice.py:292-313`).
  - Identical prompts are coalesced, as in 0.20.4.

**Refresh (#110061).**
- **What changed:** `refresh_session_coalesced` (`B:dashboard_auth/refresh_singleflight.py:86`) now handles every cookie refresh, for every provider, including `basic` and the plugin's `mobile-device`. It runs in the threadpool. Before, the refresh ran synchronously on the event loop with no coalescing (A:middleware.py:457).
  - The key is `(provider, sha256(RT))`. A success is cached for 30 s; a rejection for 5 s.
  - Every coalesced sibling goes through `_serve_refreshed` (B:middleware.py:125-137), so each one gets `Set-Cookie` with the **same rotated** AT and RT.
  - A fresh AT still never triggers a refresh (B:middleware.py:180-202).
- **Password mode:** `basic` refresh tokens have no reuse detection at either tag, so the app's serialization chain was always redundant in this mode.
- **Device/QR-pairing mode:** the mobile plugin forgives one rotation behind and revokes on two or more. At 0.20.4 concurrent refreshes could revoke the device. At 0.21.5 single-flight closes that race, but only within one process and a 30 s window.
- **What the app should do:**
  - Keep the chain while ≤0.20.4 gateways are still supported; after that it is belt-and-braces.
  - Always keep the "flush the rotated cookie before resolving" step.

**Existing bug, unrelated to the bump:** FTS search snippets use `>>>…<<<` markers at both tags (`B:hermes_state_search.py:913`), but `app:api/search.ts` `parseSnippet` expects `<b>…</b>`, so users see the literal `>>>` / `<<<`.

## 4. The wire-contract registry (#110522) and server→client requests (#110521)

- **Where it lives**
  - Source of truth: Pydantic models in `N:tui_gateway/contracts/*.py`. The registry is
    `contracts/registry.py`, with three tables: `METHODS`, `SERVER_REQUESTS`, `EVENTS` (`:47-49`).
  - Rendered by `N:scripts/gen_gateway_contracts.py` into two **committed** files:
    - `N:apps/shared/src/gateway-contract.generated.ts`: 5,657 lines. Contains `RpcMethods` (`:4670`),
      `ServerRequestMap` (`:5388`), and `BackendGatewayEventMap` (`:5434`), plus every params, result
      and payload type.
    - `N:apps/shared/src/gateway-contract.openrpc.json`: 940 KB. OpenRPC plus `x-server-requests` and
      `x-notifications`.
  - `tests/tui_gateway/contracts/test_generated.py` regenerates the files and fails CI if they are
    stale.
- **Can the app vendor it?** Yes.
  - The `.ts` file has **zero imports** and is plain types. License: MIT.
  - The shared runtime client is also vendorable: `N:apps/shared/src/json-rpc-channel.ts` (576 lines)
    and `json-rpc-gateway.ts` (706 lines, imports only the two sibling files). They use the global
    `WebSocket` and `URL`, and already implement the whole protocol:
    - the capability handshake on `gateway.ready` (`json-rpc-channel.ts:483-490`);
    - automatic `-32601` for unhandled server requests (`:69-70,317`);
    - `open_requests` replay (`:334,395,457`);
    - `session.events.since` replay after reconnect (`json-rpc-gateway.ts:135-137,482,533`);
    - the heartbeat.
  - One caveat: the app's RN socket factory passes an `Origin` header, which needs the
    `socketFactory` option.
- **How complete it is**
  - Every registered method must have a contract, or the import fails (`registry.py:1-7`).
    `assert_complete` also covers emitted event names and sent server requests.
  - Totals: 237 methods, 13 server requests, 73 events.
  - Result and payload models are `extra="forbid"` except where a field is deliberately open:
    `SessionLiveInfo` and approval params are `OpenModel`, and `JsonValue` renders as `unknown`.
  - Runtime result/payload checks **only log in production**; they raise only under
    `HERMES_TEST_ISOLATION` (`registry.py:82-92`). Treat the types as accurate but not
    runtime-guaranteed.
- **What "server→client requests" means for a client**
  - The gateway is now a JSON-RPC peer. It writes
    `{"jsonrpc":"2.0","id":"srq-…","method":<m>,"params":{session_id,…}}` and blocks the agent thread
    until a frame with the same `id` and a `result` or `error` comes back (`server_requests.py:1-29`).
  - Server request ids are always strings, so they never collide with the client's integer ids.
  - The 13 methods (`N:contracts/server_requests.py`):
    - relevant to mobile: `approval`, `clarify`, `sudo`, `secret`;
    - desktop or GUI only: `vault.unlock_prompt`, `vault.save_login`, `vault.code`, `terminal.read`,
      `preview.read`, `preview.act`, `window.read`, `tour`, `display.install.sudo`.
  - The client **must** send `client.capabilities {server_requests:true}` once per connection. The
    result lists the methods the server may send (`N:contracts/liveness.py:29-43`,
    `N:methods_voice.py:442-450`).
  - The client must answer **every** request: with a result, or with `-32601` for any method it
    doesn't handle.
  - Withdrawal: the `request.cancel {id, method, reason}` event (`timeout` / `interrupted` /
    `shutdown` / `resolved` / `session_closed`).
  - Responses are routed at `N:tui_gateway/rpc_dispatch.py:54-58`. A response for an id that is no
    longer open is dropped.
  - **The old event path is gone, not deprecated.**
    - Removed events: `approval.request`, `clarify.request`, `sudo.request`, `secret.request`,
      `*.expire`, `mcp.setup.request`, `terminal.read.request`, `preview.read.request`,
      `window.read.request`.
    - Removed RPCs: `clarify.respond`, `sudo.respond`, `secret.respond`, `mcp.setup.respond`,
      `terminal.read.respond`, `preview.read.respond`, `window.read.respond`.
    - Only `approval.respond`, `approval.pending` and `approval.received` survive, as RPCs.

## 6. Top 8 for the app, ranked by value per effort on a phone

1. **Server-request handler + `client.capabilities` + `request.cancel`.** This is a prerequisite for
   the bump. Without it, approvals are silently refused at 0.21.5.
2. **`session.interrupt` (Stop button).** One RPC, and the effect is immediate. At 0.21.5 it also
   stops background delegations and clears the queue. Show `message.complete.status==="interrupted"`
   as "Stopped", not with the Success haptic.
3. **Clarify card (single + batch, with `clarify.lock`).** Fixes the reported stall. After §1 the
   frame is already arriving, so this is mostly UI.
4. **`open_requests` replay on resume.** A push notification that opens the app to a pending approval
   or question then shows the card. Very little code once item 1 exists.
5. **`session.steer` from the composer while busy.** Handle the `rejected` result by sending the text
   as a normal prompt. This is the distinctive mobile feature, and at 0.21.5 steer text lands as its
   own user row.
6. **`session.events.since` replay on reconnect.** Mobile sockets drop constantly. Replaying the event
   ring beats today's full `GET /messages` reload and keeps live cards (subagents, todos) intact.
7. **Context ring from `message.complete.usage` / the `session.usage` event**
   (`context_percent`, `cost_usd`). The data already arrives on the socket the app holds open. Only a
   UI is needed.
8. **`subagent.interrupt` / `subagent.steer` on the existing subagent cards.** The cards already exist.
   Remember that 0.21.5 requires `session_id` and ownership.
